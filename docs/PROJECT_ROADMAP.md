# EdgeDoc Cam：项目总体计划

> 状态快照：2026-11-11。路线按阶段推进，不是硬性八周截止；每次课程、实验或决策后，按文末交接流程更新 GitHub 记录。

## 项目定位

EdgeDoc Cam 面向 LubanCat-4 V1（RK3588S、4 GB RAM）与 IMX415 摄像头，结合 Xiaomi-OCR-0，建设一套离线的文档采集、端侧推理与优化系统。项目同时服务于嵌入式 Linux/驱动、边缘 AI 部署与推理优化方向的学习和求职准备。

首版目标是：对一张平整的中英文印刷文档进行持续预览，由用户手动触发选帧，生成由应用独立持有的稳定快照，执行必要预处理，经有界 OCR 队列完成离线推理，并输出文本、Markdown，以及按需生成的 JSON 和可复核的性能、质量度量。

首版队列最多容纳 **1 个等待中的任务**；活动任务与等待任务的状态必须清楚，满队列时应有明确反馈。系统不得对预览中的每一帧运行 OCR。

### 首版范围边界

- **包含：** 单张、平整、中英文印刷文档；持续预览；手动选帧；稳定独立快照；预处理；离线 CPU OCR 主路径；有界任务队列；文本/Markdown/按需 JSON 结果；完整度量。
- **不是 V1 承诺：** 复杂表格、弯曲书页、手写、多页 PDF，以及任意复杂表单。它们可作为后续探索，不能用于首版验收承诺。

## 目标数据流与硬件边界

```text
IMX415 传感器
    ├─ I2C：传感器配置与控制
    └─ MIPI CSI-2 / D-PHY：像素数据
          ↓
RK3588S RKCIF / RKISP
          ↓ V4L2 采集缓冲区
持续预览 ── 用户选帧
          ↓ 复制为应用独立持有的快照
图像预处理
          ↓
有界 OCR 任务队列（最多 1 个等待任务）
          ↓
Xiaomi-OCR-0 CPU 后端（V1 参考与交付主线）
          ↓
文本 / Markdown / 按需 JSON + 延迟、内存、温度、质量等度量
```

I2C 承担传感器控制，MIPI 承载像素数据。现有证据分别观察到 sensor/media0 与 ISP/media1 图内的有效链路，但跨 media graph 的内部联接尚未完全证实。设备节点应通过 media graph 与格式/能力发现和验证；不得把某个 `/dev/videoX` 永久硬编码成产品假设。

4 GB 内存预算下，默认优先只保留一个主要模型实例，并限制排队快照的数量和尺寸。内存、延迟及热状态都需要通过板端实测约束。

## 阶段路线（相对周次）

| 阶段 | 重点 | 退出证据 |
|---|---|---|
| W1 / Sprint 0 | 系统与媒体拓扑、板端环境事实、CPU OCR 基线方案 | 可复现的硬件/软件基线，已知限制和 CPU benchmark 协议；没有用“驱动已绑定”代替“图像已采集” |
| W2 / L01–L02 | IMX415 媒体链路；原生 C++17 V4L2 MMAP 采集 | 单帧与短时循环证据、快照可独立解码、采集缓冲区所有权说明；L02-R1 仍需真实相机回归 |
| W3 / L03 | C++ 对象与 RAII、线程、mutex、condition_variable、有界任务队列 | 小型模拟快照队列先验证所有权、背压、停止和异常路径，再接入摄像头 |
| W4 | 快照 → 预处理 → Xiaomi-OCR-0 CPU 端到端 | 一次可复现的离线 OCR 流程；先建立正式 CPU 基线与输出质量检查 |
| W5 | 先做 PP-OCR ONNX → RKNN 的可控 NPU 闭环；再探索 Xiaomi VLM 的 RKNN/RKLLM 兼容性 | 完整记录模型、转换器、运行时、驱动、输入输出与板端验证。Xiaomi NPU 兼容性当前未知，首轮探索预算约 12 小时，并明确结论为通过、部分通过或不通过；失败不阻塞 CPU 产品 |
| W6 | 量化、质量门控、延迟、内存、吞吐 profiling 与对照实验 | 同一冻结数据与参数下的 CPU/NPU 对比，同时报告识别质量、资源和热状态 |
| W7 | 异常恢复、长时测试与可靠性 | 有限队列、推理失败、设备错误和重复启动/停止等边界均有证据；时长与环境明确 |
| W8 | Demo、实验复测、GitHub 复现、简历与面试 | 按文档从干净环境复现关键结果，并能解释取舍、测量边界和未解决问题 |

### 后端策略与决策门

1. **CPU 路径是稳定交付基线。** 保留 Xiaomi-OCR-0 的 llama.cpp GGUF CPU 路径，包含模型与视觉 mmproj 的版本/校验信息、参数和复现实验说明。
2. **NPU 是逐步验证的实验路径。** 板上存在 RKNN runtime（version string 2.3.0）和 RKNPU DRM render path，不代表已经有模型在 NPU 上成功运行。RKNN NPU 模型成功加载尚未验证。
3. **先验证可控模型链路，再评估目标模型。** PP-OCR ONNX → RKNN 用于打通转换和运行闭环；Xiaomi VLM 的 RKNN/RKLLM 兼容性保持为有限时间的探索，不预设成功。
4. **如 NPU 路线部分成功或失败，** 记录卡点、证据和已用预算，保留 CPU 可交付系统；是否继续投入由项目负责人决定。

## 最近的执行顺序

1. 在负责人批准后，按受控流程对 L02-R1 做真实相机回归，并继续调查 IMX415 日志；不改动 boot image、内核、设备树、网络、安装包或摄像头参数，除非先获得专项批准。
2. 为 Xiaomi-OCR-0 建正式 CPU benchmark：冻结输入图片、模型/参数和测量边界；区分冷/热运行，至少重复 5 次；报告 latency/P95、Peak RSS、温度、CER、输出完整性和失败情况。原始图片和私密测试文档不得上传。
3. 继续 L03：先用极小的模拟快照队列练习线程共享内存和同步，再扩展到 `mutex`、`condition_variable` 和队列。

## 结果维护规则

每次完成一讲、一次板端实验或一个设计决策，都在对应记录中更新日期、目标、环境、命令/参数、实际证据、验收结论与未解决事项。计划、理论学习、短时实验和工程验收必须分别描述；任何未取得证据的事项保持未完成状态。
