## 角色与工作流

- **项目负责人（用户）：** 决定方向和技术取舍，批准需要审批的板端实验，验收工作，并独自决定是否合并 PR。
- **导师（ChatGPT）：** 按阶段讲解系统知识，审查设计、代码和实验日志，帮助准备嵌入式 Linux / 边缘 AI 面试。
- **执行者（Codex / Work）：** 在负责人批准的边界内准备代码、检查实验、执行已获批的板端工作，并提交可审查的分支/PR。
- **GitHub：** 项目事实和学习进度的唯一持久记录；每项结论应能追溯到 PR、日志、命令或验收说明。

标准流程：教学 → 用户独立回答或参与方案设计 → Codex 在独立分支实施 → 记录实际证据 → 导师审查 → 用户决定是否合并。

### 板端与模型事实

- 板端基线：Debian 12、`6.1.99-rk3588`、IMX415 驱动绑定；RKNN runtime version string 为 2.3.0；存在 RKNPU DRM render path。这些事实没有证明模型正在 NPU 上运行。
- 本地存在 Xiaomi GGUF Q4_K_M 与视觉 mmproj 文件。正式、可复现的 Xiaomi-OCR-0 CPU benchmark 尚未完成；历史单次约 33.67 s smoke 不是基线。
- 候选 BSP 源码暗示 `write reg array error` 可能与空 `global_reg_list`（ret=0）有关，但候选源码对应的 Image 与当前 boot Image 不一致；根因未证实。
- 板卡本地墙钟与实际执行日期不一致。跨机器日志只能谨慎对时，必须记录各自时区/时钟来源，避免直接比较造成错误结论。
- 单平面 V4L2 成功设备、多内存平面设备和内核异常注入未实测。

## 操作边界

- 刷写设备、改 boot image / 内核 / 设备树 / 网络、安装依赖、改变摄像头参数，都必须先得到项目负责人的明确批准。
- 不上传模型权重、相机图像、个人文档、私密测试文档、访问令牌、密码或本地环境文件。
- CPU llama.cpp GGUF 路径保留为参考和交付主线。NPU 路径按实验验证，不假定 RKNN 模型已成功加载，也不假定 Xiaomi 模型兼容 RKNN/RKLLM。
- 4 GB RAM 设备优先单一主要模型实例并使用有限队列；避免无界积压和把每帧预览都交给 OCR。
- 任何新的实现都放到独立分支，并由 PR 审查。合并由负责人决定。
