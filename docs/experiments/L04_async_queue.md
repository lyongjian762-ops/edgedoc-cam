# L04-A：容量为 1 的异步任务队列

## 范围与基线

本实验只使用模拟像素和模拟处理函数，在电脑端运行；不连接摄像头、不调用 OCR、不更改板卡系统或配置。开始时检查到 PR #7、#8、#9 均为开放的 Draft，尚未合并；本实验从 `main` 的 `aab8c21393787e3e2567061b4873a76370b347e8` 建立独立分支，没有引入这三个草稿的提交。

## 设计

`FrameSnapshot` 包含任务 ID、宽高、行跨度、像素格式和自己持有的 `std::vector<uint8_t>`。快照禁止复制，提交使用右值引用；实际接受时才移动到队列。调用 `try_submit(std::move(frame))` 不意味着一定发生移动：返回 `Busy` 或 `Stopped` 时调用者仍持有原数据。一次移动转移 vector 的存储所有权，而不逐字节复制整张图。生产者在构造自己的快照时仍需提供独立的数据；这个实验没有声称摄像头或 OCR 链路零拷贝。

队列只保留一个等待位置。消费者取出后，当前任务由消费者持有，不占等待位置，因此最多可同时有一个正在处理、一个等待处理：

```text
生产者 → try_submit → [等待槽：0 或 1] → 消费者 → 模拟处理
                         已满：Busy         锁已释放
                         停止后：Stopped
```

互斥锁保护等待槽和停止标志；消费者用条件变量及谓词等待有任务或停止。提交不等待队列空位，但仍可能短暂等待互斥锁。返回 `Busy` 时不覆盖既有任务。`stop()` 在同一把锁下设置标志并唤醒消费者：先处理已经接受的等待任务，空队列时结束；之后的提交返回 `Stopped`。取出任务后锁随函数返回释放，再调用处理函数，因此耗时处理不会持有队列锁。

处理函数抛异常时工作线程捕获异常、记录失败次数和最后一次失败的任务 ID/异常，并继续排空；成功次数不包含失败任务。`stop_and_join()` 供所有者线程调用，并要求对象销毁前生产者已结束；`stop()` 可并发调用。处理函数借用快照，只能在调用期间使用，不能保存其引用。停止不会强制中断处理函数，因此若处理函数永不返回，排空和 join 也不会结束。析构会停止并 join；不要在工作线程自身销毁或 join 它自己。

## 构建与复现

电脑环境：Windows、CMake 3.31.6-msvc6、MSYS2 UCRT64 g++ 16.2.0、MinGW Makefiles，Debug 构建。已安装的工具通过本机 PATH 找到；无需安装新依赖。一般配置命令如下，具体生成器和编译器可按本机工具链指定：

```sh
cmake -S . -B build-l04 -DCMAKE_BUILD_TYPE=Debug
cmake --build build-l04 --parallel 2
ctest --test-dir build-l04 -V --output-on-failure
ctest --test-dir build-l04 --repeat until-fail:25 --output-on-failure
```

本机实际命令、原始输出和返回码见 [L04_async_queue_log.txt](L04_async_queue_log.txt)；其中仅将本机工作区绝对路径替换为 `<WORKSPACE>`，其余测试结果未改写。日志中的模拟程序还展示任务 2 被接受、任务 3 返回 Busy，两个已接受任务均完成。

## 实测结果与覆盖范围

2026-11-11 本机编译成功；CTest 注册了 1 个测试程序，该程序包含以下 6 个场景，全部通过。CTest 又对整个测试程序连续重复 25 次，全部通过；每次并发停止场景内部进行 25 轮竞争。重复运行有助于发现问题，但不能证明不存在所有线程调度问题。

| 场景 | 实际检查 |
| --- | --- |
| 空队列停止 | 消费者最终返回、重复停止安全、停止后的提交保留数据；此测试没有确定消费者已进入睡眠后再停止，因此不能单独证明该特定调度下的唤醒。 |
| 满队列、排空和生命周期 | 用条件变量卡住正在执行的任务；第二个接受、第三个 Busy；停止后拒绝新任务；按顺序排空，检查像素、元信息及移动后的存储地址。 |
| 处理异常 | 第一个任务抛出模拟异常，记录异常及 ID，第二个已接受任务仍完成。 |
| 多生产者竞争 | 执行任务被门闩卡住时，8 个生产者同时竞争一个等待位置，恰好一个接受、七个 Busy。 |
| 并发停止与提交 | 每轮 6 个生产者和一个停止线程同时开始，核对最多一个等待任务被接受、拒绝时数据保留、已接受任务排空；允许不同的合法竞争结果。 |
| 析构排空 | 所有者离开作用域时，已接受任务执行完成且线程被 join。 |

测试使用条件变量、promise 和 future 控制顺序。5 秒等待是失败上限，不是推测线程状态的固定睡眠；CTest 外层另有 30 秒超时。模拟演示中的短暂 sleep 仅用于模拟耗时工作，不用于测试排序。

## 尚未验证

- 尚未使用 ThreadSanitizer 或其他数据竞争检测器；尚未在 Linux/RK3588S 编译或运行。
- 空队列停止场景未严格控制到消费者已经阻塞的时刻，虽然代码通过条件变量谓词和 `notify_all()` 实现唤醒；需要增加可观测的等待握手后再单独验证该调度。
- 未连接真实图像采集、OCR、文件系统或任何设备；未测吞吐、延迟、内存上限，也未注入内存分配或线程创建失败。
- 无强制取消或超时终止正在执行的任务；本实验只实现排空策略。
